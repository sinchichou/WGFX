# 權重策略實測：內嵌 WGSL 常數 vs 二進位 storage buffer

> 這份文件記錄 `.wgx` 封裝計畫階段 2 的**前置 gate** 結果 ——
> 「把 CNN 權重從 WGSL 內嵌常數轉為二進位 storage buffer」是否值得。
>
> 實測日期：2026-11-11 · 硬體：NVIDIA Lovelace · 工具：node-webgpu (Dawn)

---

## 1. 結論（先看這裡）

**不轉。權重維持 WGSL 內嵌常數。**

| 面向 | 內嵌常數 | storage buffer | 取捨 |
|---|---:|---:|---|
| **每幀**（1920×1080，324 組權重） | **2.746 ms** | 13.044 ms | **內嵌快 375%** |
| **編譯**（Tint + 驅動） | **522 ms** | 2,356 ms | **內嵌快 351%** |
| 套件大小（全 effects 樹，deflate 後） | **4.48 MiB** | 2.72 MiB | 二進位小 39% |

在 60 fps 的即時影片擴充套件裡，**+375% 的每幀代價**只換到 4.48 → 2.72 MiB
（距 Chrome Web Store 的 2 GB 上限極遠）——**明確不划算**。

`.wgx` 因此維持「壓縮後的 WGSL 文字」這個設計，不做權重抽取。

---

## 2. 量測方法與可信度

### 2.1 為什麼第一版量測不可採信

初版 microbenchmark 量到 531% 差距，但**結果與常理相反**（它同時顯示 storage buffer
「編譯更慢」）。原因是 B 路徑的存取型態是 **cache-hostile**：每像素對 4 KB 範圍做
64 次隨機讀取，而 A 路徑的常數全進常數快取。這不代表卷積權重的真實情況。

### 2.2 正確的量測設計

第二版貼近真實 CuNNy 結構（`effects/CuNNy/*.wgsl`）：

- 權重直接**從真實效果檔抽取**（`CuNNy-4x8C-NVL` 的 324 組 `mat4x4<f32>`）
- 權重引用在 **helper 函式**內，helper 被多個 pass 共用（與真實結構一致）
- 每個 thread 都會讀到同一組權重 → 對 cache 友善
- 矩陣乘法語意為 `mat4x4<f32> * vec4<f32>`（與真實效果一致）

### 2.3 排除量測假象

- **暖機**：量測前先跑 30 幀不計時（排除 GPU 頻率爬升與首次執行效應）
- **交錯量測**：A/B/A/B/… 共 6 輪，消除順序效應
- **多輪取中位數**：並報範圍

| 輪 | inline | mat4buf |
|---:|---:|---:|
| 1 | 4.861 ms | 15.195 ms |
| 2 | 2.745 ms | 12.929 ms |
| 3 | 2.746 ms | 12.961 ms |
| 4 | 2.724 ms | 13.021 ms |
| 5 | 2.741 ms | 13.096 ms |
| 6 | 2.758 ms | 13.044 ms |

暖機後（輪 2–6）兩者的範圍**完全不重疊**（inline 2.724–2.758 / mat4buf 12.929–13.096）。

## 3. 為什麼會差這麼多

量測把編譯時間拆成兩段：

| | Tint（着色器前端） | 驅動程式（ISA 產生） |
|---|---:|---:|
| inline | 24 ms | **498 ms** |
| storage `array<mat4x4<f32>>` | 7 ms | 2,349 ms |
| storage `array<f32>`（扁平 + 手動組矩陣） | 28 ms | **186,070 ms** |

三點結論：

1. **Tint 端兩者都很快**（7–28 ms）—— 着色器前端不是瓶頸。
2. **驅動端差距巨大**：inline 常數被編碼為指令流中的立即數，由常數快取供應；
   storage buffer 讀取則走 LSU。對「每 thread 數百次矩陣乘法」的卷積，
   這個差距是結構性的。
3. **扁平 `array<f32>` + 手動組矩陣最糟**（驅動端 186 秒）—— 因為 16 次獨立載入
   破壞了向量化。若真要走 storage buffer 路徑，必須用 `array<mat4x4<f32>>`
   這種整體載入的形態。

> ⚠️ 這個結論是 **NVIDIA Lovelace** 上的結果。Intel / AMD 的常數快取行為不同，
> 可能有不同結論；本專案的開發與測試環境為 NVIDIA。

## 4. 封裝大小的取捨（真實檔案）

以真實的 `effects/` 全樹計算，比較「權重留在 WGSL 文字」與「抽成 f16 二進位」：

| 家族 | 現況 raw | 現況 deflate | 抽 f16 後 | 差異 |
|---|---:|---:|---:|---:|
| Anime4K | 2.99 MiB | 0.93 MiB | 0.42 MiB | −54.6% |
| **CuNNy** | 5.58 MiB | 1.20 MiB | 0.67 MiB | −43.9% |
| **CuNNy2** | 4.54 MiB | 1.05 MiB | 0.37 MiB | −65.3% |
| FSRCNNX | 0.18 MiB | 0.06 MiB | 0.02 MiB | −68.6% |
| NNEDI3 | 5.82 MiB | 0.97 MiB | 0.97 MiB | −0.0% |
| 其他 11 家族 | 1.05 MiB | 0.30 MiB | 0.30 MiB | ≈0% |
| **合計** | **20.06 MiB** | **4.48 MiB** | **2.72 MiB** | **−39.4%** |

**大小面確實有收益**（−39.4%），但對照效能面的 −375%，取捨不成立。

## 5. 對 `.wgx` 格式的影響

```diff
  example.wgx  (zip)
  ├── manifest.json
  ├── shaders/pass0.wgsl      # ← 權重留在這裡（壓縮後 22.3%）
- ├── weights/conv0.bin       # ← 取消：抽取的代價是每幀 +375%
  └── textures/areaTex.dds
```

- **權重維持在 WGSL 文字中**，由 deflate 壓縮（WGSL 文字壓縮率約 22.3%）
- `.wgx` 的 `resources[]` 仍保留 `weights/` 欄位規格，以備將來有**其他**效果
  （例如權重來源本來就是外部檔、或 GPU 架構差異）需要二進位化時使用
- OpenNR **不受影響**：它本來就用 storage buffer（上游架構如此），
  且其權重已由 `tools/opennr_weights.mjs` 轉為 packed-f16 二進位

## 6. 什麼時候該重新考慮

- **換 GPU 平台**時：Intel / AMD 的常數快取行為不同，應重跑本量測
- **出現「單一效果權重 > 50 MiB」**時：屆時套件大小才可能成為主要瓶頸
- **需要 GPU 常數快取無法容納的權重總量**時（NVIDIA 的 constant cache 有限）
